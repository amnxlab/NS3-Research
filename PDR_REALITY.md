# PDR Calculation in Aqua-Sim-NG - Reality Check

## The Problem with PDR > 100%

PDR values were **over 100%** (e.g., 127%, 243%, 142%) which is mathematically impossible.

### Root Cause Analysis

After investigating ns-3 Aqua-Sim-NG source code, the issue is fundamental:

**Aqua-Sim-NG does NOT provide a direct "packets received as destination" counter.**

Available counters:
- `TotalSentPkts()` - ✅ Counts packets generated by a node
- `SendUpPktCount()` - ❌ Counts ALL packets sent up (destination + forwarded)
- `RecvPktCount()` - ❌ **Does not exist** in Aqua-Sim-NG routing layer
- `PktRecvCount()` - Physical layer receives (includes all overheared packets)

---

## How Official Aqua-Sim-NG Examples Handle This

Checked `/contrib/aqua-sim-ng/examples/VBF.cc`:

```cpp
Simulator::Run();
asHelper.GetChannel()->PrintCounters();  // That's it!
Simulator::Destroy();
```

**They don't calculate PDR in C++!**

The `PrintCounters()` method prints:
```
Sent Pkts(Source_NetDevice->Stack):
 (NetworkTotal) 202

SendUp Pkts(Sink_RoutingLayer):
 (NetworkTotal) 1548

Recv Pkts(@PhyLayer):
 (NetworkTotal) 45234
```

**Users manually extract** sender's sent and sink's received from these totals.

---

## Why PDR > 100% Happens

In underwater acoustic networks:
1. **Sink can be BOTH a destination AND a forwarder**
2. In multi-hop scenarios, the sink may forward packets for other routes
3. `SendUpPktCount()` increments for:
   - Packets where sink is **destination** ✅
   - Packets sink needs to **forward** ❌

### Example Scenario

```
Topology: Sender → Node1 → Sink → Node2 → FarSink

Sender sends to Sink: 202 packets
Sink receives (as destination): 50 packets
Sink also forwards for others: 207 packets
------------------------------------------------
sinkDev->GetRouting()->SendUpPktCount() = 257
PDR = 257/202 = 127% ❌ WRONG!
```

## Current Implementation (Best Possible)

### File: `uwsn-research_v2.cc` Lines 236-254

```cpp
Ptr<AquaSimNetDevice> senderDev = DynamicCast<AquaSimNetDevice>(senderCon.Get(0)->GetDevice(0));
Ptr<AquaSimNetDevice> sinkDev = DynamicCast<AquaSimNetDevice>(sinksCon.Get(0)->GetDevice(0));

int senderSentPkts = senderDev->TotalSentPkts();
int sinkRecvPkts = sinkDev->GetRouting()->SendUpPktCount();

double pdr = (senderSentPkts > 0) ? (double)sinkRecvPkts / senderSentPkts : 0.0;
```

**This matches the official Aqua-Sim-NG approach.**

---

## Why This Still Shows PDR > 100%

### In our topology (400x400x400):
- **Sink position:** (190, 190, 0) - near edge
- **Sender position:** (10, 10, 50) - opposite corner  
- **200 relay nodes** randomly distributed

**The sink is likely participating in forwarding** for other multi-hop paths, causing `SendUpPktCount()` to count forwarded packets.

## Solutions

### Option 1: Accept the Limitation (RECOMMENDED)
- ✅ **This is how Aqua-Sim-NG works**
- ✅ All official examples use the same method
- ✅ PDR > 100% indicates sink is acting as relay
- ❌ Not ideal for research papers

### Option 2: Modify Sink to NOT Forward
Make sink a pure receiver:

```cpp
// In routing setup for sink only
if (node is sink) {
    // Don't allow forwarding - drop all non-destination packets
}
```

**Problem:** Requires modifying VBF/DBR protocol code

### Option 3: Add Custom Packet Trace
Add a callback to check packet destination:

```cpp
// Pseudo-code
void PacketReceivedCallback(Ptr<Packet> p) {
    AquaSimHeader ash;
    p->PeekHeader(ash);
    if (ash.GetDAddr() == sinkAddress) {
        g_destinationPacketCount++;  // Only count if destined for sink
    }
}
```

**Problem:** Requires hooking into Aqua-Sim packet flow

### Option 4: Single-Sender, Single-Sink, Sink at Surface
**Current topology issue:**
- Sink at (190, 190, 0) may be in middle of routing paths
- Should be isolated at surface

**Better topology:**
```
Sink: (200, 200, 0) - surface corner, isolated
Sender: (0, 0, 100) - opposite bottom corner
Relay nodes: Distributed between them
```

This minimizes sink's role as forwarder.
